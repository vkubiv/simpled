simpled 2.3.0 has the controller report the environment's health to CloudWatch and email
alarms, and lets `simpled status`, `simpled logs` and local env specs read `aws`
secrets without AWS access.

## Health alarms in CloudWatch

- **`controller.cloudwatch`** (Docker) has the controller publish the environment's
  health every minute (namespace `Simpled`: `Health` for the environment and each
  deployment, `GatewayHealth`, `CertDaysLeft`) and keep the alarms on it, which
  email `alarm_email` through the SNS topic `simpled-<name>-health`:

  ```yaml
  controller:
    host: ops
    cloudwatch:
      alarm_email: [ops@example.com]
  ```

- No Lambda or prober: `simpled:<name>:silent` fires when the metrics stop, so a dead
  server, Docker or controller is reported too. The others fire when a deployment
  (3 minutes) or the gateway (2 minutes) is down, when the environment has not been
  healthy for 15 minutes, and when a certificate has had under 14 days left for an
  hour.
- The controller keeps the topic, its subscriptions and the alarms in line with the
  env spec at start and every 6 hours, and deletes only alarms under
  `simpled:<name>:`. Each new address gets one confirmation email from AWS.
- It uses the EC2 instance role (or `AWS_*` variables). The role needs the policy in
  the reference, and the instance an IMDSv2 hop limit of 2, as the controller runs in
  a container. See [CloudWatch](../reference.md#cloudwatch).

## Secrets without AWS access

- **`simpled status` and `simpled logs`** read the controller token from the env
  spec's `controller.read_token` (else `manage_token`) when `SIMPLED_TOKEN` is not
  set.
- **`aws-secrets.local.json`** next to the env spec stands in for Secrets Manager
  wherever simpled reads an `aws` secret on this machine: the controller token for
  `status`/`logs`, and `local` env specs. It is keyed by secret id, a listed secret's
  `jq` path is applied the way `jq -er` does on the deploy target, and an unlisted
  secret is read with the AWS CLI. Keep the file out of git.
- `prepare-deployment` for a remote target never reads it on its own and warns when
  it is there; `--aws-secrets-file <path>` reads every `aws` secret from that file
  into the output.

## Before you upgrade

Nothing to change: `controller.cloudwatch` and `aws-secrets.local.json` are opt-in,
and env specs and deploys from 2.2.0 work as they are.
